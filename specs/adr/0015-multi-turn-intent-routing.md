# ADR-0015：多轮对话意图路由升级（会话级路由 + 短句继承 + 改写复用）

## 元信息

- 日期：2026-08-13（2026-08-14 更新为已实施）
- 关联：module-063（执行简报）、agent/router.py（意图路由）、rag/engine.py:237（路由调用点）、ADR-0003（intent 校验四层）、module-043/055/056（意图路由演进）、query_rewrite（分诊式改写链路）

## 背景：现状（代码实测，2026-08-13）

- `engine.py:237`：`intent_result = await router_agent.classify(request.query)`——**只传当前这一句，会话历史没有进意图路由**
- `router.py:203`：`async def classify(self, query: str)` 签名无 history 参数
- 但历史其实已在请求里（`engine.py:230` 日志 `history=%d`）、也已用于生成侧（`engine.py:258` `*request.history`）——**路由阶段是唯一没吃历史的一环**
- 后果：多轮对话中"为什么""那图谱呢"这类省略句/指代句，单句无特征 → 大概率误判 `casual_chat` 或 `realtime`，走了错误分支

## 动机

用户说话是"上下文依赖"的：省略句、代词、指代句在单句里没有特征，必须有前文才能判定。意图路由是单句识别，天然漏掉这类场景。需要：① 会话级路由（历史进路由）② 短句意图继承（规则层，零成本）③ 复用现成改写链路根治省略句。

## 决策 1：会话级路由（核心，半天）

- `classify(query, history[-4:])`——把最近 4 轮历史与当前 query 一起喂给路由
- LLM 侧 few-shot 加一句"考虑前文对话上下文判断意图"；L4 分类器（bge-m3+LR）特征里拼接最近一轮 query 的向量
- 历史窗口取最近 3-8 轮（业界共识区间：百度千帆 3 轮 / lobehub condenser 8 轮 / zenvanriel 5-10 轮），本项目取 4-6 轮——**更早轮次几乎不影响指代，还费 token**
- 兜底：`request.history` 为空时行为与现状完全一致（零回归）

## 决策 2：短句意图继承（规则层，零成本，2 小时）

- 规则：query 去除语气词后 **长度 < 6 字符 且 无 FTS 术语/图谱实体命中** → 继承上一轮 intent（不调 LLM）
- 中文特化（CSDN 实践）：**先去语气词**（哦/呢/呀/请问等）再判长度——"为什么呀"→"为什么"，触发继承
- 复用现有 `_deterministic_confirm`（FTS 术语/图谱实体/规则表）判断"有没有新特征"——**有特征必须重新路由**（防话题漂移）
- 上一轮 intent 为 knowledge 时继承 knowledge；为 casual_chat/realtime 时同样继承（防"知识库问完突然说今天天气"被继承，靠"无特征"门槛挡住）

## 决策 3：复用分诊式改写链路喂路由（根治省略句，1 天）

- 关键洞察：**现有分诊式改写（FTS 术语静态分诊 → 模糊才 LLM 改写 → 保真预检余弦回退 → 原/改写并行择优）就是业界 Hybrid 改写（规则 + LLM + 原/改写并行）的标准形态**（吴师兄/zenvanriel 均推荐此结构）——不是新增能力，是"改写结果多喂一个消费方"
- 流水线：`"为什么" → 改写为"为什么用 RRF 融合" → 路由按改写后 query 判 → 必是 knowledge`——**一次改写，路由和检索两头受益**（业界 Conversational RAG condenser 模式：轻量 LLM 把模糊句改成自包含 query）
- 改写用便宜快模型（qwen-7b 级即可，temperature=0.0，max_tokens=512——掘金实践）；本项目降级链 qwen→zhipu→deepseek 可直接复用
- **改写必须保守**（防 over-rewriting 翻车）：保真预检余弦回退必须保留；改写失败/低置信 → 用原始 query（零回归）

## 决策 4：工具调用历史作附加规则信号（可选增强，2 小时）

- 上一轮 tool_calls 含 `search_knowledge`/`generate_answer` → 本轮短 query 强制走 knowledge
- 定位：**规则层补充信号，不是替代**（确定性、零 token）；与决策 2 的"无特征继承"叠加
- 注意：这是本项目的推理（基于 re_search 双组设计），非业界主流文献直接结论——面试可讲"工具轨迹是意图的强信号"

## 业界对标（调研验证，2026-08-13）

- **百度千帆 Query 改写实测**（官方文档，三大场景）：企业知识库——召回率 62.5%→**89.2%**、回答准确率 58%→**87.5%**、平均对话轮次 3.2→**1.8**（-43.8%）；电商客服——一次解决率 68.5%→**90.2%**、响应时长 4.8s→**2.1s**（-56.3%）
- **lobehub Conversational RAG skill**：condenser LLM（Haiku 级）改写 + last-8-turn 截断 + 每轮两 LLM（廉价改写 + 全量合成）
- **指代消解本质**：核心是"补全信息来源 = 对话历史的 Query 重写"（吴师兄第 7 章）；实体显著度栈（nemorize）为进阶方向
- **改写质量三指标**（zenvanriel）：自包含清晰度 / 意图保持 / 检索提升——可复用到 golden 评测集（加"多轮追问"题型）
- **三大失败模式**（callsphere）：lost antecedent（改写着不知道"它"指谁→加长历史窗口或强模型）/ over-rewriting（改写加了用户没说的上下文→提示词要求保守）/ stale retrieval（缓存失效→话题转移信号失效）

## 三个坑（实施时盯住）

1. **历史不能全塞**：取最近 4-6 轮（会话层有 50 条上限，全塞拖慢路由且无收益）
2. **改写要保守**：保真预检回退必须保留；防 over-rewriting（业界第一翻车原因）
3. **话题漂移**：继承只对"极短且无新特征"的 query 生效；正常长度 query 必须重新路由（"知识库问完突然问天气"不能继承）

## 实施顺序（本项目，按性价比）

| Step | 内容 | 工作量 | 收益 |
|---|---|---|---|
| 1 | 会话级路由（classify 加 history[-4:] + 短句继承规则） | 半天 | ⭐⭐⭐ 解决"为什么"主力场景 |
| 2 | 改写结果喂路由（复用现成链路） | 1 天 | ⭐⭐⭐ 根治省略句 + 检索受益 |

## 面试话术（30 秒）

> "多轮对话的意图路由，单句识别会漏掉省略句和指代句——'为什么'这种 query 没有前文特征，会被误判成闲聊。生产级方案是三层：第一，路由时带最近几轮历史（会话级路由）；第二，极短无特征的 query 继承上一轮意图（规则层，零成本，先去语气词再判长度）；第三，复用我的查询改写链路，把省略句改写成自包含 query 再路由和检索——一次改写两头受益。业界标准叫 conversational query rewriting，轻量 LLM 做 condenser。中文场景有实测参照：百度千帆上线后召回率 62.5%→89.2%、准确率 58%→87.5%、平均轮次 3.2→1.8。我踩过的坑：历史不能全塞（4-6 轮够）、改写必须保守（保真预检回退防 over-rewriting）、继承只对极短 query 生效（防话题漂移）。工具调用历史是附加信号，放规则层不花 token。"
