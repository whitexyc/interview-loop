# ADR-0002 — Agentic RAG 简历表述与代码实现对齐决策

- 状态：已采纳（面试口径校准）
- 日期：2026-08-08
- 背景：对 `docs/简历/07-项目经历-精简版.md` 逐词深挖，对照 `.claude/worktrees/m8-knowledge-panel/ai_service` 代码，发现若干简历表述与代码实现存在出入，需统一面试口径，避免被追问时自相矛盾。

## 决策 1：三通道检索的表述口径

**问题**：简历写"三通道混合检索……三路加权融合"。代码中 `hybrid_retriever` 仅对 FTS + 向量做 alpha 加权融合（alpha=0.3，`rag/retriever.py`）；图谱是第三路，仅在流式路径 `engine._retrieve()` round 0 与向量检索 `gather` 并行，然后**按文档 id 合并去重**（`engine.py`），graph_score 独立存在，不参与 hybrid_score 加权公式。非流式 `chat()` 路径完全不含图谱通道。

**决策**：面试表述统一为分层描述——"召回层 FTS+向量 alpha 加权融合得 hybrid_score；图谱作为第三通道并行检索，按 id 合并进候选集，图文档以实体命中数归一化的 graph_score 参与排序；非流式快捷路径为降延迟只走两通道。"

**理由**：如实分层描述比笼统说"三路加权融合"更经得起追问；若被追问"为什么图不参与加权"，可答两通道分数是连续相似度（可归一化加权），图命中是离散计数、语义上更像证据补充。

## 决策 2：0.96 命中率口径

**问题**：简历只写 0.96。完整口径（简历 01）：30 题 golden 中 23 题有效（剔 7 题无覆盖/标注歧义），三通道融合 Top-5 命中 0.96，FTS 0.43 / 向量 0.87。

**决策**：面试开场主动交代"23/30 题有效、自标注、7 题无覆盖跳过、标题层级前缀容错判定命中"。同时注意评估脚本 `--mode hybrid` 实为两通道，图谱贡献由 `--ablate`（graph_only vs hybrid）单独量化——若面试官较真"三通道融合 0.96 如何复现"，需主动区分"评估口径的 hybrid=两通道"与"流式链路三通道"。

## 决策 3：测试用例数口径

**问题**：简历写 355 个 pytest 用例；代码 `tests/test_*.py` 中 `def test_` 函数统计为 358（28 个文件）。

**决策**：报数以 `pytest --collect-only -q | tail -1` 实际收集数为准，统一口径（参数化用例展开、helper 是否计入会致差异）。建议简历改为"350+ pytest 用例"留余量。

## 决策 4：模块数量口径

**问题**：简历写"42 个模块"。specs/ 下 module-* 目录实际列到 module-042（含跳号，如缺 008/011/012/036-041 等），代码注释中 module 编号出现约 24 个。

**决策**：简历改为"约 40 个迭代模块"或明确口径"模块迭代至 042"；面试说"40 多个迭代模块、四角色 AI 协作闭环"即可。

## 决策 5：HyDE 未进简历精简版

**问题**：HyDE（假设文档嵌入，`engine._hyde_expand`，带 Redis 缓存）是检索质量关键提升手段，简历 07 未提及。

**决策**：被问"检索怎么提质量"时主动讲 HyDE（LLM 生成假设回答模仿文档语言风格 → 用其向量检索 → 提升召回；独立缓存键 300s TTL；失败降级原始 query）。
