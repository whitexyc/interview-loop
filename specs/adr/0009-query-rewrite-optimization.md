# ADR-0009 — Query 改写优化方案（分诊式改写 + 保真校验 + 评测闭环）

- 状态：✅ **已实施**（2026-08-10 module-049 落地：分诊式改写 + 保真预检 + 并行检索择优 + 评测闭环；全量 567 测试全绿；真实模式评测待 DB+LLM 环境补跑验证增益）
- 日期：2026-08-10
- 背景：用户连续追问 query 改写——现状问题、企业级方案、专业文档、分诊判断逻辑。调研业界方案（RRR/Multi-Query/Step-Back/子查询分解/RewriteGen）后，产出分诊式改写方案。本 ADR 记录现状问题 + 新方案 + 业界对标 + 实施顺序。

## 现状基线（代码事实）

- **反思驱动改写**：意图路由 → 首轮检索（原始 query / 流式 HyDE 扩展）→ 反思判不充分 → LLM 返回 `rewritten_query` → 二次检索 → **结果与原始合并** → 最多 3 轮（engine.py:236/641）
- **HyDE 扩展**（流式 round 0 前，engine.py:562）：LLM 生成假设回答模拟文档风格，提升首轮召回（HyDE ≠ 改写）
- 改写是**检索后发现问题才触发的补救动作**，非预检索优化

## 现状问题诊断（8 项）

| # | 问题 | 影响 |
|---|---|---|
| 1 | **改写时机晚**——只有反思判不充分才改写，事后补救非事前优化 | 首轮检索可能召回差，白跑一轮 |
| 2 | **单候选无打分**——LLM 一次生成一个 rewritten_query | 改错就是错方向，无从选择 |
| 3 | **无评测闭环**——eval_runs 无 query rewrite 专项 | 改得好坏靠感觉，无法迭代 |
| 4 | **HyDE 与改写两套独立**——流式先 HyDE、反思后再改写 | 两次 LLM 调用成本叠加，互不感知 |
| 5 | **依赖 LLM 主观**——改写必要性/质量无客观信号 | 与反思充分性同坑（LLM 单点判断） |
| 6 | **合并而非择优**——改写结果与原始合并 | 可能引入噪声（改写后检到离题文档） |
| 7 | **无子查询分解**——复杂/多跳问题无分解 | 复杂问题召回差 |
| 8 | **无改写路由**——所有不充分都改写 | 浪费 LLM 调用 |

## 新方案：分诊式策略化改写

```
query 进来
├─ ① 静态分诊（零成本，FTS 术语命中，不用向量检索）
│   ├─ 术语命中 → 精确 → 直接检索（一次）→ 生成
│   └─ 术语不命中 / 有代词 → 模糊 → 走改写路径
├─ ② 模糊路径
│   ├─ 保真预检：LLM 改写 → rewritten_query 与原 query 余弦 < 0.6 → 回退原话
│   ├─ 并行检索：原 query + 改写 query 各检索一次（记录各自 top-1 绝对余弦）
│   └─ 择优：改写检索绝对余弦 > 原检索 → 用改写；否则回退原结果
└─ ③ 生成
```

**三个关键设计点**：
1. **分诊是静态 FTS 术语命中，不是"检索后看拿不拿得到答案"**——复用 `router.py::_kb_terms`（jieba 分词 → 过滤功能词 `_FUNCTION_STOPWORDS` → 专有术语查 FTS 倒排命中），毫秒级零成本；"精确"判据是词表对得上（检索质量），不是"答案对不对"（生成太贵）
2. **对比用绝对余弦**（module-035 口径，跨 query 可比）——不能直接比两个 query 的分（不同 query embedding 不可比）
3. **保真预检可省一次检索**——改写 vs 原 query 余弦 < 阈值直接回退，连检索都不用花

**解决什么问题**：

| 新方案组件 | 解决的现状问题 |
|---|---|
| 静态 FTS 分诊（术语命中直接检索） | 问题 1、8——改写从事后补救变事前分诊，精确 query 不再白跑、不浪费改写 |
| 保真预检（改写 vs 原 query 余弦回退） | 问题 2、6——改写跑偏检索前拦截，防合并噪声 |
| 并行检索 + 绝对余弦择优 | 问题 2、6——单候选变双候选对比，改错可回退 |
| 改写评测闭环（Recall@K 前后对比） | 问题 3——用数据量化增益，支撑迭代 |

## 业界对标（2026-08-10 调研）

- **Rewrite-Retrieve-Read**（Ma et al. EMNLP 2023 / arXiv:2305.14283）：检索前重写框架 + RL 可训练重写器；硬数据——**HotpotQA 上不重写的 RAG 比不 RAG 还差**（多跳问题直接检索引入噪声）
- **Multi-Query + RRF 融合**（LangChain 标配）：生成 N 变体并行检索 + Reciprocal Rank Fusion，不押单个改写
- **改写路由**（Microsoft Cloud Blog 三分类：规则/ML/混合）：判断"要不要改写"，不对称投放省成本
- **子查询分解 / Step-Back**（arXiv:2310.06117）：复杂问题拆解/抽象一步再检索
- **对话上下文化**（Databricks Docs 多步 query understanding）：多轮 query 结合历史改写成独立完整问题
- **RewriteGen**（南京大学学报 2025）：RL 统一重写+检索决策+生成
- **MaFeRw**：多维度反馈（query 相似度+文档相关性+生成质量）训练重写器

## 实施顺序（按性价比）

1. **P0 · 检索前主动重写**（RRR 思想）：改写从"反思后补救"提前到"检索前"
2. **P0 · 多候选 + RRF 融合**：生成 2-3 个改写变体并行检索 + RRF 融合（不押单个）
3. **P0 · 改写评测闭环**：建 query rewrite 评测集（复用 golden 30 题）对比"原始 vs 改写"Recall@K/MRR
4. **P1 · 改写路由**：简单精确 query 跳过改写（静态 FTS 分诊），模糊才改写
5. **P1 · 对话上下文化**：多轮 query 结合历史改写成独立完整问题
6. **P2 · 子查询分解**：检测到复杂/多跳问题才拆 2-4 个子问题
7. **P2 · 专用重写器训练**：小模型 + RL（奖励=下游答案质量），替代每次 LLM 改写

## 面试话术

> "我现在的改写是反思驱动的被动补救——时机晚、单候选、无评测。升级方案是分诊式改写：先用 jieba 分词提取专有术语查 FTS 倒排，词表对得上就是精确 query 直接检索，不用改写；模糊 query 才让 LLM 改写，改写后先做保真预检（改写和原 query 余弦低于阈值直接回退），再和原 query 并行检索、用绝对余弦择优——谁检索出的文档相关度高用谁。这套方案解决三个问题：改写从事后补救变事前分诊、单候选改错可回退、加上 Recall@K 评测闭环能量化增益。业界依据是 RRR 论文——不重写的 RAG 在多跳问题上比不 RAG 还差。长期可以做专用重写器（RL 训练，奖励连下游答案质量，推理毫秒级）。"
