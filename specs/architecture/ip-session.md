# IP 会话与限流机制

> **日期**: 2026-07-30 | **分类**: 架构设计 | **涉及模块**: ai_service, frontend

---

## 1. 问题

### 1.1 刷新丢消息
知识库问答页面在浏览器刷新后，聊天记录全部丢失。用户每次刷新都要重新开始对话，体验极差。

### 1.2 无访问控制
AI 服务没有请求频率限制，单个客户端可以无限制地调用 LLM 生成，导致:
- API 费用失控（LLM 按 token 计费）
- 服务端资源被恶意占用
- 其他用户的服务质量下降

---

## 2. 解决思路

采用"前端 + 后端"双保险策略：

```
┌─────────────────────────────────────────────────────┐
│                    用户浏览器                          │
│  ┌──────────────────┐    ┌──────────────────┐        │
│  │  localStorage     │    │  聊天页面         │        │
│  │  (消息持久化)      │◄───│  ChatPage        │        │
│  └──────────────────┘    └────────┬─────────┘        │
│                                   │ HTTP/SSE          │
└───────────────────────────────────┼──────────────────┘
                                    │
┌───────────────────────────────────┼──────────────────┐
│                     AI 服务                          │
│  ┌──────────────┐  ┌──────────────┐                 │
│  │  IP 限流中间件 │─→│  IP 会话缓存  │                 │
│  │  (滑动窗口)    │  │  (内存 dict)  │                 │
│  └──────────────┘  └──────────────┘                 │
│                          │                           │
│                     ┌────▼────┐                     │
│                     │ RAG 引擎 │                     │
│                     └─────────┘                     │
└─────────────────────────────────────────────────────┘
```

### 2.1 前端 localStorage
- **机制**: 每次 `messages` 状态变化时，自动序列化到 `localStorage['rag_chat_messages']`
- **恢复**: 组件挂载时从 localStorage 读取，反序列化后恢复对话
- **清空**: 用户手动清除浏览器数据时自然清空
- **优势**: 无网络依赖、零延迟、后端无状态
- **局限**: 仅单浏览器有效，切换设备/浏览器无法共享

### 2.2 后端 IP 会话缓存
- **机制**: 内存 dict，key 为客户端 IP，value 为最近 50 条消息
- **端点**:
  - `GET /ai/chat/sessions` — 获取活跃会话列表
  - `GET /ai/chat/sessions/{ip}/messages` — 获取指定会话的消息
- **消息保存**: chat 端点在返回结果后，自动将 `{user_msg, assistant_msg, sources}` 追加到 IP 对应的缓存中
- **裁剪**: 超过 50 条时丢弃最旧的消息
- **优势**: 跨浏览器/设备可用（同一 IP 下）、后端可做分析

### 2.3 双保险的组合效果

| 场景 | localStorage | IP 会话 | 效果 |
|------|-------------|---------|------|
| 正常使用，刷新页面 | ✅ 恢复 | ✅ 可查 | 立即恢复 |
| 清除浏览器数据 | ❌ 丢失 | ✅ 可查 | 通过后端 API 恢复 |
| 切换网络（IP 变化） | ✅ 恢复 | ❌ 新 IP | 前端恢复 |
| 两者都不可用 | ❌ | ❌ | 空对话开始 |

## 3. 限流方案

### 3.1 算法：滑动窗口计数

```
请求到达
  │
  ├─→ 取客户端 IP（X-Forwarded-For → remote_addr）
  │
  ├─→ 获取该 IP 的请求时间戳列表
  │    剔除窗口外的时间戳（< now - 60s）
  │
  ├─→ 剩余请求数 ≥ 20?
  │     ├─ 是 → 返回 429 Too Many Requests
  │     │       Retry-After: 剩余等待秒数
  │     └─ 否 → 记录本次时间戳，放行
  │
  └─→ 正常处理请求
```

### 3.2 实现位置

`src/ratelimit.py` 实现了核心限流逻辑，通过 FastAPI middleware 注入：

```python
# main.py
@app.middleware("http")
async def rate_limit_middleware(request: Request, call_next):
    # health 路径跳过
    # 提取 IP → 检查限流 → 放行或 429
```

### 3.3 配置

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `max_requests` | 20 | 窗口内最大请求数 |
| `window_seconds` | 60 | 时间窗口（秒） |

### 3.4 边界情况

- **分布式部署**: 当前内存 dict 只在单实例有效，多实例需改用 Redis sorted set
- **代理转发**: 通过 `X-Forwarded-For` 获取真实客户端 IP，避免误限代理 IP
- **限流头信息**: 返回标准 `Retry-After` 头，方便客户端适配
